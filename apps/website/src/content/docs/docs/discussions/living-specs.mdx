Keep one lasting spec for each part of your code, updated by the runs that change it. Here is why. A feature spec describes one change. Once it ships it is a record of something that happened. A year later, current behavior is the sum of thirty specs minus the parts later specs undid.

A **living spec** describes a **capability**, a piece of behavior your code keeps having. You register it once, keep it next to the code, and update it from the runs that change that code.

A feature spec is done when the feature ships. A living spec never is. Nothing updates one automatically, and the sections below say who does.

## Turn it on

Living specs stay off until you add `living-specs.yml` at the repo root.

```yaml
enabled: true
exempt: ["*.config.*", "*.test.*", "**/migrations/**"]
capabilities:
  - name: spec-viewer
    match: ["src/features/spec-viewer/**"]
    spec: src/features/spec-viewer/spec-viewer.spec.md
  - name: workflows
    match: ["src/features/workflows/**", "speckit-extension/workflows/**"]
```

| Key | What it does |
| --- | --- |
| `enabled` | The opt-in. Without a registry, or with this unset, every living-specs command acts as if the feature were absent. |
| `exempt` | Globs that never count as drift. Default: `*.config.*`, `*.test.*`, `**/migrations/**`. |
| `name` | The capability id, and its folder name when the location is derived. |
| `match` | Globs whose files belong to it (minus the capability's own `exclude` globs). |
| `spec` | Where the spec lives. Optional. |

An older `livingSpecs:` block in `.specify/companion.yml` is still read. If both exist, `living-specs.yml` wins.

## Where the spec lives

**Colocated.** Give a `spec:` path and the spec sits beside the code as `<something>.spec.md`.

**Central.** Omit `spec:` and it goes to `capabilities/<name>/<name>.spec.md`. The older `spec.md` name is still found. This suits code spread across many folders.

You can mix both. The sidebar's Living Specs tree mirrors your choice, and `/speckit.companion.living-move` switches a capability between layouts later.

Each spec has two siblings named from its stem. `<stem>.rules.md` holds conventions as plain bullets for people and assistants. It is not loaded by the workflow. `<stem>.coverage.md` maps requirements to tests, and feeds the coverage count. Only `living-adopt` writes a rules file. Nothing writes a coverage file, so a capability without one shows no number, which looks like zero coverage.

- **Most specific wins.** A file matching several capabilities goes to the one with the longest literal path prefix, then by name.
- **A nested registry is a separate project.** The scan stops at a subfolder with its own `living-specs.yml`.
- **Orphans.** A spec file no capability claims appears under **Orphans**, hidden when there are none.

## The commands

All seven are `/speckit.companion.living-<verb>` and come from the Companion Spec Kit extension. Without it, neither they nor the Living Specs view exist.

| Command | What it does |
| --- | --- |
| `living-adopt` | Drafts a spec for one code area you name, then registers it. Assistant work, marked as a starting point. |
| `living-sync` | Rewrites the affected specs from your current changes. Assistant work. |
| `living-drift` | Lists source files changed since each spec was last committed, split into those that went through the workflow unfolded and those the spec never saw. Committed history only. `--working` adds uncommitted edits. |
| `living-coverage` | Reports what each coverage file says. `--capability <name>` limits it. |
| `living-show` | Prints a requirement list, one requirement, or the requirements for one file. Read-only. |
| `living-validate` | Checks spec and delta shape: no scenario, missing WHEN or THEN, duplicate heading, delta pointing nowhere. Read-only. |
| `living-move` | Moves a capability between layouts and rewrites the registry, after confirming. |

Drift, coverage, show, validate and move are scripts, so their answers are repeatable. Adopt and sync are prompts, so their quality is your assistant's.

## How a run folds back

A **delta** is a block a run adds to its own feature spec to say what it changed about a capability.

```markdown
## ADDED Requirements
<!-- capability: spec-viewer -->

- The viewer re-anchors a stored comment onto the freshly rendered page when its tab reopens.
```

The other headings are `## MODIFIED Requirements`, `## REMOVED Requirements` and `## RENAMED Requirements`. A block without a capability comment goes to whichever capability the changed files matched.

At mark-complete the assistant writes the blocks and a script folds each into its capability spec. The fold is deterministic, and folding twice changes nothing. Because the blocks live in the feature spec first, they show up in that feature's diff for review.

The standard specify, plan, tasks workflow emits no deltas. Each capability a run loaded must end with a delta or a recorded skip note. If not, the fold prints a receipt saying the loop did not close. It never blocks the run.

## What stays manual

- A spec stays current only if a delta was written at mark-complete, or someone ran `living-sync`.
- Drift and coverage never gate anything. They are read-only and always exit zero. Wrap them in CI if you want a gate.
- A capability with an uncommitted spec, or a CI checkout with too little history, is skipped with the reason named. The all-clear line means every capability was actually examined.
