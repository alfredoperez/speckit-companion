**I want to add my own commands or attach my own steps.** There are two ways, and they are easy to mix up.

| | Custom command | Node hook |
| --- | --- | --- |
| What it is | A slash command you run when you want | Work attached inside a Companion command |
| Where it lives | VS Code settings | `.specify/companion.yml` in your repo |
| How it runs | From a quick pick or the viewer footer | As part of that command |

A **node** is one section inside a Companion command, and it is what a hook anchors to. To replace the whole workflow instead, see [Pick a pipeline](/docs/discussions/pick-a-pipeline).

## Add a custom command

Everything in `speckit.customCommands` appears in **SpecKit: Run Custom Command**.

```json
{
  "speckit.customCommands": [
    "review",
    { "name": "pr", "title": "Create PR", "command": "/speckit.pr", "step": "tasks", "requiresSpecDir": false }
  ]
}
```

A bare string like `"review"` becomes `/speckit.review` and shows in the quick pick only. The object form also reaches the viewer footer.

| Property | What it does |
| --- | --- |
| `name` | Identifier. Used as the command when `command` is omitted. |
| `title` | Label in the picker. |
| `command` | The slash command to dispatch. |
| `step` | Where it is offered: `spec`, `plan`, `tasks` or `all` (default). |
| `tooltip` | Hover text. |
| `requiresSpecDir` | Add the spec directory to the command. Default `true`. |
| `autoExecute` | Run it in the terminal automatically. Default `true`. |

Write `${specDir}` in the command to place the spec directory yourself. Otherwise it is appended.

In the viewer, object-form commands appear in the footer's **Other actions** menu for the step you set. The menu is hidden when the spec is closed, at its closure gate (Mark Completed or Reactivate), or when the list is empty.

## Attach a hook

Hooks add your own work before or after a named node. The file holds changes only.

```yaml
commands:
  implement:
    hooks:
      before:
        handoff:
          - { type: command, run: "npm test" }
          - { type: prompt, text: "Confirm the CHANGELOG is updated." }
      after:
        implement-exec:
          - { type: node, ref: review }
```

Hooks at one anchor run top to bottom.

| Type | What it is |
| --- | --- |
| `command` | A shell command. Needs a provider with a terminal tool. |
| `prompt` | An inline instruction dropped in at that point. |
| `skill` | `{ type: skill, ref: <name> }`: asks the assistant to invoke one of your skills. |
| `node` | Your node file at `.specify/companion/nodes/<id>.md`. |

Add `background: true` to start a hook without waiting for it. Use it for independent work like tests or notifications, never for anything that writes the run record.

The Pipeline Builder, opened from the Specs toolbar, can write hooks for you. See [the Pipeline Builder guide](/docs/guides/pipeline-builder).

## Other keys in companion.yml

| Key | What it does |
| --- | --- |
| `commands.<name>.nodes` | Replaces a command's node order. Dropping a node that a kept node reads from is refused. |
| `commands.<name>.phases` | Renames and regroups phases. A phase name becomes a hook anchor. |
| `workflow` | Names a file under `.specify/companion/workflows/` that replaces this configuration. `shipped` selects none. |

A node file at `.specify/companion/nodes/<command>/<node id>.md` replaces the shipped node, and `_frame.md` in that folder replaces the step's preamble.

## What "runs" means

Nothing executes `companion.yml`. Your assistant reads it at run time, because instructions for doing so are appended to each command. A hook is a strong convention, not an enforced step. If something must never be skipped, put it in CI.

| Situation | What happens |
| --- | --- |
| No `companion.yml` | Shipped defaults, no warning |
| File cannot be parsed | Shipped defaults and one warning. Nothing partial is applied. |
| Hook anchored to a missing node | Warning, anchor skipped |
| `type: node` hook with a missing file | Error |
