A feature spec describes one change. Once it ships it is a record of something that happened. A year later, current behavior is the sum of thirty specs minus the parts later specs undid.

A **living spec** describes a **capability**, a piece of behavior your code keeps having. You write it once, keep it next to the code, and update it from the runs that change that code. Living specs come with the Companion Spec Kit extension.

<DocFigure src="living-specs-explained-x16x9.png" caption="Specs for a shipped feature go quiet. Capability specs settle next to the source files they describe, each with a coverage count or a drift flag." />

## Start with one area

Open the **Living Specs** pane in the sidebar and click **Set up living specs**. It asks one question: keep the specs together in one folder, or beside the code they describe.

Then pick the area you explain most often and run `/speckit.companion.living-adopt` on it. Your assistant reads the code and drafts a spec for it. Read the draft. It is the fastest way to learn whether you drew the boundary in the right place.

## How a spec stays current

When a Companion run finishes, it writes what it changed about each capability into its own feature spec, and a script folds that into the living spec. You review it in the feature's diff like any other change.

A run with plain Spec Kit does not do this. Run `/speckit.companion.living-sync` afterwards.

## What stays manual

- Nothing updates a spec on its own. It is current only if a run folded its changes in, or someone ran `living-sync`.
- Drift and coverage never block anything. They report and always exit zero, so a CI job that should fail has to read their output.
- A capability whose spec is not committed yet is skipped, and so is one in a CI checkout with too little history. The report names each one and why.
- The coverage count comes from a file you write. No file means no number, which is not the same as zero.
