The Overview shows what a run did, on one page: why the spec exists, how long each phase took, what was checked, what was decided and which requirement got which test. Click **Overview**, the first entry in the rail, to open it.

<DocFigure
  src="overview-annotated-16x9.png"
  alt="The Overview of a finished run with its per-phase timing called out: run status, expectations, verified checks with their commands, decisions with rejected alternatives, and the coverage table."
  caption="A finished run. The Run overview strip shows a time for a phase only when both of its ends were recorded."
/>

It is read from the **run record**, a `.spec-context.json` file next to the spec. Nothing on the page runs or re-checks anything.

## When it appears

| Situation | What you get |
| --- | --- |
| A feature spec whose run recorded something | The Overview, as the first entry in the rail |
| A spec that was never run | No Overview. The spec opens on its document. A status, a current step or your own review comments do not count as a run. |
| A living spec | Its own overview, not this one |
| `speckit.viewer.activityPanel` set to `false` | No Overview |
| The Companion Spec Kit extension is not installed | A thin page and a banner offering the install, because most of what the page reads never gets written |

A region with nothing recorded does not render, so a thin page means a thin record.

## The regions

The page has seven regions, top to bottom. Most have a title and, on the right, a count. Skim the counts first. They tell you where to read closely.

### Intent

The one sentence the run answers to. Under it sit the time each phase took, then a card with the approach, any living specs the run updated or only read, the working area, and a sizing line such as `Sized simple: 6 files, 6 tasks projected`.

Read it first. If it does not match what you expected, stop there.

### Run overview

It sits inside Intent, right under the sentence. One entry per phase with the time it took, and the run's total as active time: the time the phases took, without the waits between them.

<DocFigure
  src="live-run-timing.png"
  alt="The Run overview strip: Specify 5 minutes 40, Plan 7 minutes 36, Tasks 3 minutes 25, Implement 34 minutes 45, and 51 minutes 28 active on the right."
  caption="A time for each phase, and the total on the right."
/>

| A phase reads | Meaning |
| --- | --- |
| A duration | Both ends of the phase were recorded |
| Blank | One end is missing. The page declines to guess. It is not a zero. |
| "folded into Plan" | The run merged this phase into an earlier one |
| No end yet | The phase is running. Its live timer is on the rail tab. |

When some phases have no time, the head reads "Timing coverage: N of M phases", or "Timing not recorded".

### Expectations

What must stay true on one card, and what was left out on purpose on the other. Something you expected is not in the diff? Check the second card before calling it a gap.

<DocFigure
  src="live-run-expectations.png"
  alt="The Expectations region, titled The fence around the work. One card lists two things that must stay true, and a second lists three things deliberately out of scope."
  caption="Constraints on top, declared non-goals under them."
/>

### Verified

Each check with its command and outcome. The count reads `3 checked`, or `2 checked · 1 reported`.

A checked row is a command the recorder ran itself, and it keeps the exit code. A reported row, marked with a quote, is the assistant's own account of something that could not be run. So `0 checked · 5 reported`, as in this picture, means nothing was run for you. Use the list to learn which commands to run yourself.

<DocFigure
  src="live-run-verified.png"
  alt="The Verified region, titled What was checked, and what happened. The count reads 0 checked, 5 reported. The first four rows show, each with a quote mark, what was checked, the word pass, and the command."
  caption="Reported rows, each with a quote mark: the assistant's account, not a run."
/>

### Decisions

The choice, why, and what was rejected. The first three show and the rest sit behind "Show N more decisions".

The rejected line is the useful part. It is what a later session would otherwise rediscover the slow way.

<DocFigure
  src="live-run-decisions.png"
  alt="The Decisions region, titled Choices future work should not have to rediscover. Three numbered decisions, each with a Why line and a Rejected line."
  caption="Each decision keeps its reason and the option it turned down."
/>

### Coverage

Each requirement, the tasks that delivered it and the tests that exercise it. This table most often carries bad news. Untraced requirements sort first, and six rows show before "Show all N requirements". The count reads `4/7 traced`, in a warning tone until every requirement has evidence.

<DocFigure
  src="live-run-coverage.png"
  alt="The Coverage region, titled Requirement to task to test. The count reads 4 of 4 traced. Four requirements, each with its task ids on the left and a test count on the right."
  caption="Requirement to task to test, with every requirement traced."
/>

| Evidence reads | Meaning |
| --- | --- |
| "N tests" | The requirement names N tests, and every file is on disk |
| "No test linked" | The requirement names no test |
| "N tests not found" | It names N tests, and none of the files is on disk |
| "K of N found" | It names N tests, and only K of the files are on disk |

The check is that the file exists. Nothing runs the test.

### Run log

Collapsed until you open it: the latest activity, when the phases started and ended, and one line per task with who recorded it and when. Open it when you need to know what one task did or which files a run touched.

## How far to trust it

- **Where it comes from.** The Companion Spec Kit extension writes `.spec-context.json` during runs, and the VS Code extension only reads it. Commit the file and the record travels with the branch.
- **Timestamps differ in trust.** Step boundaries and per-task finishes are written by a script. Clarify and analyze closes, and the smaller stages inside plan and tasks, are reported by the assistant to the second. The run only says "X active" when specify, plan, tasks and implement all measured cleanly.
- **The log only grows.** A write that would publish a shorter history is rejected.
- **The install banner.** Dismiss it once and it stays gone, or set `speckit.companion.installPrompt` to `false`.
