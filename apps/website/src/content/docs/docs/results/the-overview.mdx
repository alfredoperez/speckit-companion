The Overview is the first tab in the viewer's rail. It reads the run record, a `.spec-context.json` file next to the spec, and nothing on the page runs or re-checks anything.

## What's measured and what's reported

| On the page | Where it comes from | How far it goes |
| --- | --- | --- |
| Step boundaries and task finishes | A script writes them | Measured |
| Clarify and analyze closes, and the stages inside plan and tasks | The assistant reports them, to the second | The assistant's account |
| A blank phase time | One end of the phase is missing | Not a zero. The page won't guess. |
| "X active" total | Shown only when specify, plan, tasks and implement all measured cleanly | Excludes the waits between phases |
| A checked row in Verified | A command the recorder ran, with its exit code | Measured |
| A reported row in Verified, marked with a quote | The assistant's account of something that couldn't be run | Nothing was run for you |
| Evidence in Coverage | The viewer checks that each named test file is on disk | Nothing runs the test |
| Intent, Expectations, Decisions | The assistant writes them during the run | As good as the run that wrote them |

The Companion Spec Kit extension writes the record and the VS Code extension only reads it. The log only grows: a write that would publish a shorter history is rejected. Commit the file and the record travels with the branch.

## The regions

A region with nothing recorded doesn't render, so a thin page means a thin record. Most regions have a count on the right, which tells you where to read closely.

### Intent and Run overview

The one sentence the run answers to, then the time each phase took, then a card with the approach, the living specs the run updated or read, the working area and a sizing line such as `Sized simple: 6 files, 6 tasks projected`. If the sentence doesn't match what you asked for, stop there.

<DocFigure
  src="live-run-intent.png"
  alt="The Intent region of a finished run: one sentence about letting a member set their own profile photo, the time each phase took, then a card with the approach, the living specs the run updated and read, and the working area."
  caption="Intent, with the approach and the living specs the run touched."

A phase reads as a duration, as blank, or as "folded into Plan" when the run merged it into an earlier phase. A phase that's still running has no time here, and its live timer is on the rail tab. When some phases have no time, the total is replaced by "Timing coverage: N of M phases" or "Timing not recorded".

### Expectations

One card holds what must stay true and the other what was left out on purpose. When something you expected isn't in the diff, check the second card before calling it a gap.

### Verified

Each check with its command and outcome. The count reads `3 checked`, or `2 checked · 1 reported`. A count of `0 checked · 5 reported`, as below, means no command was run, so use the list to learn which commands to run yourself.

### Decisions

Each decision keeps the choice, the reason and what was rejected. The first three show and the rest sit behind "Show N more decisions". [Review with comments](/docs/steps/review-with-comments) is how you say one is wrong.

<DocFigure
  src="live-run-decisions.png"

  caption="Each decision keeps its reason and the option it turned down."
/>

### Coverage

Each requirement, the tasks that delivered it and the tests that exercise it. Untraced requirements sort first, and six rows show before "Show all N requirements". The count reads `4/7 traced` in a warning tone until every requirement names a test.

<DocFigure
  src="live-run-coverage.png"
  alt="The Coverage region, titled Requirement to task to test. The count reads 4 of 4 traced. Four requirements, each with its task ids on the left and a test count on the right."
  caption="Requirement to task to test, with every requirement traced."
/>

| Evidence reads | Meaning |
| --- | --- |
| "N tests" | The requirement names N tests, and every file is on disk |
| "No test linked" | The requirement names no test |
| "N tests not found" | It names N tests, and none of the files is on disk |
| "K of N found" | It names N tests, and only K of the files are on disk |

### Run log

Collapsed until you open it: the latest activity, when each phase started and ended, and one line per task with who recorded it and when.

## When there's no Overview

A spec that was never run opens on its document, and a status, a current step or your own review comments don't count as a run. Setting `speckit.viewer.activityPanel` to `false` removes the tab. Without the Companion Spec Kit extension you get a thin page and a banner offering the install, because most of what the page reads never gets written.

## Status, resume and doctor

All three need the [Companion Spec Kit extension](/docs/install) and work with any assistant.

| Question | Command | What it does |
| --- | --- | --- |
| Where does this spec stand? | `/speckit.companion.status` | Reports the current step, its status, the decisions recorded so far and the next action. Changes nothing. |
| I stopped halfway. How do I carry on? | `/speckit.companion.resume` | Finds the next step, carries the recorded decisions into scope and sends that step's command. In implement it continues at the next unchecked task. |
| Did the run do what it says it did? | `/speckit.companion.doctor` | Recomputes what happened and reports problems. Read-only. |

Resume is also the play button on a spec's row in the sidebar. On a spec that's already implemented, completed or archived, it reports that the run is complete and sends nothing.

<Actions>
  <CodeLine command="/speckit.companion.doctor" prompt={false} />
</Actions>

With no arguments the doctor checks the active spec. `--feature-dir specs/042-export-csv` checks one spec, `--all` checks every spec, `--json` gives a machine-readable report, and `--chat` also reads the assistant's session transcript to explain failed or abandoned work.

| It finds | For example |
| --- | --- |
| Unfinished work | A step that started and never finished, or a task ticked in `tasks.md` with nothing recorded for it |
| A step doing the next step's work | Plan content in the spec, a task list in the plan, code written before implement |
| A step that closed having verified nothing | Implement finished but no test or check ever ran |
| A missing file | A step that closed without the document it promised |
| Why a spec didn't complete | The write was refused, it never arrived, or it landed and the display disagrees |

Every check says whether it ran, was skipped and why, or doesn't apply, so a check that couldn't look never reads as clean. The doctor reports and stops there. To explain a failed capture it reads `specs/<NNN>/.trace.jsonl`, where every capture call writes one line, and that file is safe to delete.
