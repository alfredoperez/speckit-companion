The spec viewer opens your spec markdown as a page instead of a file. Same bytes on disk, laid out so you can read them fast.

<MediaSlot
  feature="spec-viewer"

  wide

## The tour

1. **Header.** The spec's name, a status badge, the branch, and the creation date. It reads the run record next to the spec, the same file the Specs sidebar reads, so the two never disagree.
2. **Run strip.** Small facts at the right of the header: tasks done out of total, requirements traced, checks, elapsed time, and a pull request link when one was recorded. It shows only what the badge and the rail don't already say.
3. **Pipeline rail.** One entry for each step that writes a document, plus the Overview at the top.
4. **Document.** Your markdown, with requirements, scenarios and tasks drawn as rows and chips.
5. **Outline.** "On this page" lists the headings and follows where you are. A **Subsections** toggle adds the third level.
6. **Footer.** The next step, plus archive, complete, regenerate and refine.

Two badges read differently from the stored status: `tasking` shows as **Creating Tasks** and `ready-to-implement` as **Tasks Created**. In-progress statuses get an accent tint, finished ones a quiet green, idle ones a muted tone.

## The pipeline rail

The rail lists the documents of the workflow the spec recorded when it was created. A custom workflow gets its own rail.

<MediaSlot
  feature="workflow-documents"
  caption="Plan is open, with its Research and Data Model files nested under it. The highlight moves as you switch documents."
/>

- **Steps that only act don't appear.** Implement, Mark Complete and any action-only custom step have no document, so their actions live in the footer.
- **Sub-documents nest under their step.** Research, data model, and a step's `checklists/` or `contracts/` files sit under it. Other files in the spec folder show as related documents.
- **A narrow pane folds the rail into a row of chips.**

Each entry is in one state:

| State | Look |
| --- | --- |
| Done | Check mark. Its document exists. |
| Current | Highlighted. It is the document you are reading. |
| In flight | Spinner and a timer. The step is running. |
| Locked | Disabled, with a tooltip saying why. Only when a step ahead is running and this document doesn't exist yet. |
| Not started | Plain. Its document doesn't exist yet. |

<MediaSlot
  feature="step-rail"
  caption="Specification, Plan and Tasks each carry a check. Tasks is the one being read, drawn as phases with P1 and P2 chips."
/>

Current means the tab you are reading, not where the run is. Open an earlier document mid-run and the header and footer still report the real state. Clicking a tab never moves the run.

During implement, a live percentage counts the checked boxes in `tasks.md`. It sits on the implement entry when the workflow gives it one, otherwise on the last document tab.

## What the document adds

- **Requirement rows.** A bullet like `- **FR-001** The system must ...` becomes a labeled row. Any prefix of two to five capital letters and a number qualifies, so FR, NFR, SC and your own prefixes all work.
- **Acceptance scenarios.** Given, When and Then are emphasized in place. Each scenario stays one sentence.
- **Task phases.** `## Phase N: Title` becomes a phase header with MVP and P1 to P5 chips. A task like `- [ ] **T001** [P] [US2] Add the parser` becomes a checkbox with chips: `[P]` runs in parallel, `[US#]` names the user story. Sub-bullets fold into a details group.
- **Mermaid diagrams.** Each diagram gets zoom out, Reset and zoom in. There is no pan or fullscreen.
- **A stale banner.** A document generated before the one above it changed gets a banner with a **Regenerate** action. It warns, it never locks.

Anything that doesn't match these shapes renders as ordinary markdown.

## Comments

Hover a paragraph, heading, list item, task, requirement or scenario and a comment button appears. Code blocks, tables and diagrams have none. Comments pin under their line, and **Refine** hands the pending ones to your assistant. [Review and refine](/docs/guides/review-and-refine) covers the flow.

## The footer

The main button is the next step, named after it: **Plan**, **Tasks**, with a line above reading `Next: Plan`. Pressing it records the current step as done, starts the next one, and sends that step's command to your assistant.

Beside it sit Archive, Reactivate, Mark Completed, Regenerate and Refine.

- **Confirm and undo.** Archive, Complete and Reactivate need two clicks: the first shows "Confirm?" for three seconds. Regenerate waits behind a five-second **Undo** toast.
- **Spec Kit's own commands.** **Clarify** shows on Spec, **Checklist** on Plan, **Analyze** on Tasks.
- **Other actions.** Custom commands you define in settings collect in a collapsed **Other actions** menu. See [Pick a pipeline](/docs/discussions/pick-a-pipeline).

There is no forward button in six cases, and none of them is a fault:

- the implement step, where closing belongs to Mark Completed
- you are viewing a tab that isn't the current step
- a later step is already in the history
- the step never started
- the step is running (the line reads "Step running, actions unlock when it settles")
- the spec is implemented, completed or archived ("Run complete" or "Archived, read-only")

## Living specs look different

A living spec has no rail. It gets a flat tab strip: Overview, then Spec, Rules and Coverage for whichever files exist. Its header shows requirement and scenario counts, the globs it covers, where it lives, and an `N/M covered` count when a coverage file exists. A drift chip and an **Update** button appear when matching source files changed after the spec was last committed.

<MediaSlot

Requirements transcribed from existing code carry an **adopted** badge with an **Approve** control. **Approve all N** does the tier at once, with a five-second **Undo**. A drafted spec leads its title with a **DRAFT** badge. Comments on a living spec live in the open tab only. [Living specs](/docs/discussions/living-specs) explains what these files are.

## Good to know

- **Broken run record.** If `.spec-context.json` can't be parsed, the viewer renders the spec read-only and offers **Reset context**. It moves the broken file to a timestamped backup and writes a fresh one. The check runs only when a spec first opens.
- **Creating a spec.** **SpecKit: New Spec** opens a dialog: describe the feature, pick a workflow, attach images if you like. **Create Spec** stays disabled until you type something. There is no still of this dialog on this page yet.
- **Offline.** Fonts and icons ship inside the extension. Syntax highlighting and Mermaid load from a CDN, so offline you get plain code blocks and diagram source.
- **Reduce Motion** is honored everywhere.
