The spec viewer shows your spec markdown as a readable page. The file on disk is unchanged.

## The tour

1. **Header.** The spec's name, a status badge, the branch and the creation date.
2. **Run strip.** Tasks done, requirements traced, checks, elapsed time and a pull request link.
3. **Step rail.** One tab for each step that writes a document, plus the [Overview](/docs/anatomy/anatomy-of-the-overview) at the top.
4. **Document.** Your markdown, with requirements, scenarios and tasks drawn as rows and chips.
5. **Outline.** "On this page" lists the headings and follows where you are.
6. **Footer.** The next step, plus archive, complete, regenerate and refine.

## Read the step rail

<MediaSlot
  feature="step-rail"
  caption="Specification, Plan and Tasks each carry a check. Tasks is open, drawn as phases with P1 and P2 chips."
/>

| Look | Meaning |
| --- | --- |
| Check mark | Done. The document exists. |
| Highlighted | Current. This is the tab you are reading. |
| Spinner and timer | In flight. The step is running. |
| Disabled, with a tooltip | Locked. A step ahead is running and this document does not exist yet. |
| Plain | Not started. |

Clicking a tab never moves the run. Steps that only act, such as Implement and Mark Complete, have no tab. Their actions live in the footer.

## What the document adds

- **Requirement rows.** A bullet like `- **FR-001** The system must ...` becomes a labelled row. Any prefix of two to five capital letters and a number works.
- **Acceptance scenarios.** Given, When and Then are emphasized in place.
- **Task phases.** `## Phase N: Title` becomes a phase header with MVP and P1 to P5 chips. In a task line, `[P]` runs in parallel and `[US2]` names the user story.
- **Stale banner.** A document generated before the one above it changed gets a banner with **Regenerate**.

## Comment on a line

Hover a line and a comment button appears. **Refine** hands the pending comments to your assistant. [Review and refine](/docs/guides/review-and-refine) covers the flow.

## Use the footer

The main button is the next step, named after it, with a line above reading `Next: Plan`. Press it and the viewer records the current step as done, starts the next one and sends its command to your assistant.

**Regenerate** redoes the current step. **Other actions** holds Spec Kit's **Clarify**, **Checklist** and **Analyze**, plus your [custom commands](/docs/guides/customize). At the end of a run the footer offers **Mark Completed**, **Archive** and **Reactivate**.

No forward button is normal while a step runs, after a run is complete, or when you are reading a tab that is not the current step.

## A living spec looks different

<MediaSlot
  feature="living-specs"
  caption="A capability spec in the same viewer: globs instead of a branch, a coverage count instead of a status."
  wide
/>

A living spec has a flat tab strip instead of a rail. Its header shows the code it covers and an `N/M covered` count. A drift chip and an **Update** button appear when that code changed after the spec was last committed. [Living specs](/docs/discussions/living-specs) explains what these files are.

## Good to know

- **Two badges are renamed.** The stored status `tasking` shows as **Creating Tasks**, and `ready-to-implement` as **Tasks Created**.
- **Broken run record.** If `.spec-context.json` cannot be parsed, the viewer shows the spec read-only and offers **Reset context**, which backs the file up first.
- **Adopted requirements.** In a living spec, requirements drafted from existing code carry an **adopted** badge and an **Approve** control.
- **Offline.** Syntax highlighting and Mermaid load from a CDN, so offline you get plain code and diagram source.
