Plan reads the spec and decides how to build it: the approach, the files and structure involved, and the technical choices. This is where technology enters. The spec stays about what and why.

## What it writes

| File | What is in it |
| --- | --- |
| `plan.md` | A summary, a check against the [constitution](/docs/steps/constitution), and the project structure |
| `research.md` | What the assistant looked up, and what it chose |
| `data-model.md` | The entities and their fields |
| `contracts/` | Interfaces the change exposes |

Only `plan.md` is always written. The Companion workflow writes the others as the size of the change warrants. For a change sized simple, it keeps the summary and folds the rest into it, and [Specify](/docs/steps/specify) has usually written that short plan already.

The Companion plan step can also add four kinds of block to `plan.md` when the change calls for them: the functions a change reaches, a note pinned under one line of code, a lifecycle you can click through, and a rough screen. See [Customize hooks](/docs/customize/hooks) and the [plan block references](https://github.com/alfredoperez/speckit-companion/blob/main/apps/speckit-extension/docs/call-paths.md).

When [living specs](/docs/results/living-specs) are on, plan reads the specs for the capabilities in scope before it designs anything.

## Check the plan before moving on

**Checklist**, under **Other actions** in the footer, is Spec Kit's command for a quality checklist on the plan. If you edit the spec after the plan was written, the plan shows a stale banner with **Regenerate**.
