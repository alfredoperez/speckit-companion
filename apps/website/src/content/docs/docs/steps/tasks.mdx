Tasks turns the plan into `tasks.md`, a checklist in the order the work has to happen. It is the map [Implement](/docs/steps/implement) follows.

## How the list is laid out

| In `tasks.md` | Meaning |
| --- | --- |
| `## Phase N: Title` | A phase. The Companion workflow makes one per user story, after a shared setup. |
| `- [ ] T004 ...` | One task, with its checkbox |
| `[P]` | The task can run alongside its neighbours |
| `[US2]` | The user story the task serves |
| A join line between groups of tasks | Everything above it must finish before anything below starts |

The Companion workflow groups each phase into waves separated by those join lines. Tasks inside a wave are independent of each other.

## Check the list before implementing

**Analyze**, under **Other actions** in the footer, is Spec Kit's command that cross-checks the spec, the plan and the tasks for consistency.

**Create GitHub issues**, in the same menu, sends Spec Kit's `/speckit.taskstoissues`: one GitHub issue per task. It needs a GitHub remote and the GitHub MCP server in your assistant, and it creates real issues, so run it when the task list is settled. Spec Kit works on the feature of your current branch; Companion names this spec's tasks file in the request and asks the assistant to stop if the two differ.
