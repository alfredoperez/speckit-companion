The SpecKit icon in the activity bar opens a container with four views: Specs, Living Specs, Steering, and Settings & Feedback.

<MediaSlot
  feature="specs-sidebar"

  caption="Three of the four views, and the division of labour between them: your work, the standing instructions around it, and the specs that outlive any one change."
/>

Only two of them show on a fresh install with just the VS Code extension. Living Specs appears once the Companion Spec Kit extension is installed, and Settings & Feedback is hidden until you turn it on. So a first run usually looks like Specs and Steering, and that's correct, not a broken install.

The whole sidebar is a native VS Code tree, so the editor owns row height, indentation, keyboard navigation, and theming. You can reorder the views yourself: the order here is the default, not a lock.

A note about the pictures on this page. The Specs view is a native TreeView, so it can't be driven by Storybook the way the spec viewer can. The sidebar art in these docs is a presentational recreation, drawn from fixture rows and measured against DevTools snapshots of the real tree. Treat it as an accurate drawing, not as a capture.

## Specs

### Three groups, each carrying its own count

Specs group into **Active**, **Completed**, and **Archived**, and each group header carries a live count. A group with nothing in it doesn't appear at all.

Active is expanded by default and the other two start collapsed. Individual spec rows start collapsed too, so a workspace with hundreds of finished specs opens to a short list.

Which group a spec lands in is read straight from the run record next to it. There's no separate index. A spec in `specs/515-readable-spec-names/` reads as "Readable Spec Names" in the tree, with the slug staying the identifier underneath.

### The description line and the tooltip

An in-flight spec's row shows the active task and how long ago it last moved, in the form `T004 · 22h ago`. The relative time is measured from the most recent history entry, not from when the step started, so it answers "when did anything last happen here".

Hover the row and a tooltip repeats the same three facts in full words: the slug, the status, and the last activity.

### What each icon means

| Row | Icon | What it says |
| --- | --- | --- |
| Active group | Pulse | Specs in progress |
| Completed group | Filled check, in the theme's passed color | Specs you marked complete |
| Archived group | Archive box | Archived specs |
| Spec, no recorded step | Plain beaker | Created, nothing captured yet |
| Spec, step in progress | Blue beaker | A workflow step is the current one |
| Spec, implemented | Yellow beaker | Implement finished, your confirmation hasn't |
| Spec, completed | Green beaker | You marked it complete |
| Spec, running now | Spinner | A step is running at this moment |

The yellow one is worth learning. An implemented spec sits in **Active** on purpose: the pipeline got through implement, but nobody has confirmed it done, and burying it under Completed would hide that.

No status here rides on color alone. The icon shape, the group, the description line, and the tooltip each carry it independently, and the tooltip says in words when a step is running.

### Document rows carry their own state

Expand a spec and you get its documents, plus any related files in the folder. Those rows hold their own state rather than inheriting the parent's.

| Icon | Label | Meaning |
| --- | --- | --- |
| Green check | Complete | The step is done and the file holds real content |
| Blue filled dot | In Progress | The current step, or a step counted done whose file is still a stub |
| Hollow circle | Not Started | The file exists, the workflow hasn't reached this step |
| No icon, with a `not created` note | Not Created | The file isn't on disk, and the row offers no open or reveal action |

Read "complete" narrowly. It's a presence heuristic, not a judgement about the writing: a file counts as complete when it has more than three non-blank lines.

### The toolbar

The Specs title bar shows four actions in a fixed order: Filter, Sort, More Actions, and New Spec as the trailing primary. The filter fuzzy-matches on both the slug and the recorded spec name, and submitting an empty value clears it. Everything else, including collapse and expand and the Spec Kit upgrade entries, lives behind More Actions.

### Acting on several specs at once

Select several specs with shift-click or cmd-click and you can mark, archive, or reactivate them in one action. Group headers carry the same three as bulk actions over everything currently visible in that group.

Those two facts combine in a way worth knowing before you use them: an active filter narrows what a bulk action touches, because "visible" is what the filter left.

### Resume, on hover

An active or tasks-done row shows a Resume action on hover, but only when the Companion Spec Kit extension is installed. There's no stock equivalent.

Resume reads the run record, works out where the spec stopped, and dispatches one command to your assistant. If the run stopped inside implement, it names the next unchecked task and continues from there instead of restarting the step. It sends text. It doesn't run the workflow, and it gets nothing back.

### The one badge the sidebar sets

When the Companion Spec Kit extension isn't installed, the Specs view carries a single-dot badge tooltipped "Install SpecKit Companion", and VS Code aggregates that dot onto the activity bar icon, so it's visible even with the view collapsed. A pinned first row offers the same install in words. Both go away the moment the extension is present, with no reload.

That dot is the only badge the sidebar itself sets. The status badges you see on a spec, like **Specifying** or **Completed**, live in the spec viewer's header, not in the tree.

## Living Specs

A **capability** is a piece of behavior your codebase keeps having, rather than one change you made to it. A **living spec** is the durable spec for one capability. This view lists them.

/>

The view appears only when the Companion Spec Kit extension is installed, and it starts collapsed.

It's a directory tree rather than a flat list, so its shape mirrors where the capability specs actually live: a spec at `src/features/specs/specs.spec.md` shows up as a leaf under `src`, then `features`. Below the capabilities sits an **Orphans** group holding spec files no capability claims, omitted entirely when there are none.

Each capability row carries two numbers the extension works out for itself, without dispatching anything to your AI.

**Coverage** is how many of that capability's requirements have evidence recorded against them. It appears only when the capability has a coverage file beside its spec, which is a file you write rather than one anything generates. No coverage file means no number, which on screen looks exactly like zero coverage. The two are not the same thing.

**Drift** means source files matching that capability changed since its living spec was last committed. When they have, the row's icon turns the warning color. The lookup is bounded by a timeout, so a slow repository renders the row as it would otherwise rather than stalling the tree.

The title bar carries Refresh, Adopt Code Area, and Sync. The whole view is gated on a `living-specs.yml` at the repo root with `enabled: true`. The [living specs guide](/docs/guides/living-specs) covers the registry and the commands.

## Steering

A **steering document** is a standing instruction, not a per-run one. A spec says what to build this time; a steering document says how this project builds anything.

The view gathers what your AI provider already reads, plus Spec Kit's own project files, into one tree next to your specs. It doesn't invent a format, and nothing in it is read by the extension when it dispatches a step. The [steering guide](/docs/guides/steering) has the tree shape, the authoring actions, and the provider boundary.

## Settings & Feedback

Four rows and nothing else: Open Settings, Report a Bug, Request a Feature, and Rate on Marketplace. It's hidden by default; turn on `speckit.views.settings.visible` to get it. `speckit.views.steering.visible` is the matching switch for Steering, which is on out of the box.

## What the sidebar won't tell you

It doesn't know whether a document is finished. It knows whether the file has more than three non-blank lines.

It runs two things and dispatches everything else. The coverage and drift numbers on a Living Specs row are computed locally, from files on disk and from git. Everything else, Resume, Adopt, Sync, and every steering authoring action, builds a command and hands it to the assistant you configured. Once it's handed over, the extension gets no completion callback. It reads what lands on disk.

Nothing here blocks. Drift and coverage are read-only reports that always exit zero. A CI job wrapped around them can treat their findings as a gate. The commands themselves never are.
